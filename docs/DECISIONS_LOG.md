D-019 — Session cookie Secure flag comes from config (`SESSION_COOKIE_SECURE`), defaulting to True in production and False in local development/tests. Reason: Host header is client-controlled and must never decide security flags ("localhost.evil.com" matches startswith("localhost")); explicit configuration provides a reliable toggle. Status: Approved.
D-020 — Identical 404 for missing and not-owned projects. Reason: Returning 403 Forbidden on a project owned by another user reveals that the project exists, allowing project enumeration probing. Returning 404 with identical message and structure hides resource existence entirely. Alt: return 403 Forbidden for cross-user attempts. Status: Approved.
D-021 — Project name rules: strip leading and trailing whitespace, require 1 to 100 characters. Reason: Prevents empty, whitespace-only, or excessively long names in UI and database. Enforced in both request schemas (ConfigDict(str_strip_whitespace=True) + Field(min_length=1, max_length=100)) and service validation. Whitespace-only returns 422. Alt: unstripped names or longer limits. Status: Approved.
D-022 — Pagination limits: GET /projects default limit 50, maximum limit 100 (Query le=100, limit > 100 returns 422), offset >= 0 with maximum offset 1,000,000 (Query le=1_000_000, offset > 1,000,000 returns 422). Response remains a plain JSON list. Reason: Prevents unbounded DB queries, memory spikes, and SQLite integer overflow while keeping client deserialization simple. Alt: unpaginated list or wrapped envelope {items, total}. Status: Approved.
D-023 — Project list ordered by id ascending. Reason: Provides deterministic pagination and chronological insertion ordering for project listing. Alt: order by updated_at descending. Status: Approved.
D-024 — Integer parameter bounds: Path parameters for integer IDs (project_id) are bounded to 1 <= id <= 2**63 - 1 (signed 64-bit SQLite integer max). Reason: SQLite integer columns are 64-bit signed. Sending values exceeding 2**63 - 1 causes SQLite driver conversion OverflowError resulting in 500 Internal Server Error. Bounding path parameters ensures FastAPI/Pydantic returns 422 Unprocessable Entity instead. Status: Approved.
D-025 — Explicit Origin check for state-changing requests: Added OriginCheckMiddleware that checks the Origin header on POST, PUT, PATCH, and DELETE requests. If Origin is present and not in cors_origins_list, it returns 403 Forbidden {"detail": "Origin not allowed."} without calling the route handler. Requests without an Origin header are allowed (for CLI/testing). GET, HEAD, and OPTIONS are unaffected. Registered inside CORSMiddleware so CORSMiddleware remains outermost. Reason: Simple CORS requests (e.g. text/plain POST) are sent without preflight; CORS only prevents response reading in browsers, not server execution. Furthermore, same-site is broader than same-origin (ports/subdomains). An Origin check prevents cross-origin state changes. Status: Approved.

## Known limitations
- Duplicate-email 409 reveals registered emails: Returning 409 Conflict on registration with an existing email allows account enumeration via signup probing.
- Rate limiter is in-process, keyed by email only, and can be used to lock out a victim: An attacker submitting repeated wrong passwords for a known victim's email will trigger a 60-second lockout for that victim. (Note: 15-minute window tracking and 10,000-key dictionary pruning were implemented in T2.4-fixes).
- Per-IP limiting and Argon2 CPU flood must be handled at a reverse proxy: Because Argon2id is intentionally CPU and memory intensive, distributed unauthenticated POST /auth/login floods can exhaust server CPU; in production, connection-rate and IP-rate limiting must be enforced at an ingress / reverse proxy layer (e.g. Nginx, Cloudflare) before requests reach the Python backend.
- `__Host-` cookie prefix: The session cookie currently uses the name `session` rather than `__Host-session`. Using `__Host-` requires HTTPS (Secure=True), path=/, and no Domain attribute. In local HTTP development, browsers reject `__Host-` cookies. When deploying to production with HTTPS, adopting `__Host-session` provides defense-in-depth against subdomain cookie tossing.
- Security headers and CSP for the frontend: Production frontend deployment should configure standard HTTP security headers (Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, Permissions-Policy) in Next.js configuration or edge proxy.
- No fetch timeout: The frontend `apiRequest` module does not currently wrap requests in an `AbortSignal.timeout()` or timeout timer. A hung server or stalled network connection could leave UI buttons in a pending state until browser default timeout.
- API_BASE_URL silently falls back to localhost if unset in a production build: `NEXT_PUBLIC_API_BASE_URL` defaults to `http://localhost:8000` when undefined. In a production build where environment variables are omitted or misconfigured, the frontend would attempt to reach localhost. Production deployment pipelines must enforce this variable.
- Repositories commit inside each function: Currently, repository functions (`create_project`, `update_project`, `delete_project`, `create_user`, `create_session`) invoke `db.commit()` internally. Before multi-step workflows like document ingestion and chunking in T4, transaction boundaries should be moved to the service layer (Unit of Work pattern) to allow atomic rollback across multiple tables.
- Deployment requires frontend and API on the same site for SameSite=Lax cookies: Browsers do not attach SameSite=Lax cookies on cross-site asynchronous requests (fetch/XHR), requiring the frontend and backend to share the same registrable domain (e.g. `app.example.com` and `api.example.com`).
- Project DELETE removes only the database row: DELETE /projects/{id} deletes the row in SQLite. Downstream artifacts (stored PDF files in T3, chunks and vector embeddings in T4) will not be cascade-deleted by the database; T3 and T4 must explicitly implement file and vector cleanup when a project is deleted.
- Integer IDs are guessable: Sequential integer primary keys can be traversed/enumerated. This is acceptable because all queries strictly scope by owner_id in the data layer and return an identical 404 for missing and non-owned projects, preventing data leaks or existence probing. Alt: UUIDs.
